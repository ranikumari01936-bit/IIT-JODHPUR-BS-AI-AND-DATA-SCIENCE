Answers

a. Why does the Likes table need both User ID and Post ID?
It needs both because UserID identifies who liked the post, while PostID identifies which post was liked.

b. What does one row in the Likes table represent?
One row represents one user liking one particular post.

c. Can one user like multiple posts?
Yes. One user can like many different posts.

d. Can one post receive likes from multiple users?
Yes. Many different users can like the same post.

e. What type of relationship exists between Users and Posts when likes are considered?
A Many-to-Many (M:N) relationship exists.

One user → can like many posts.
One post → can be liked by many users.
The Likes table acts as a bridge/junction table between Users and Posts.

Answers

a. Which tables have a One-to-Many relationship?

Users → Posts
Users → Likes
Posts → Likes

b. How does the Likes table help represent a Many-to-Many relationship between Users and Posts?
The Likes table stores both UserID and PostID. This records which user liked which post, allowing many users to like many posts.

c. Why is a separate Likes table useful?
A separate Likes table keeps each like as a separate record. It avoids storing a large list of users inside the Posts table and makes it easier to add, remove, and count likes.

Short Explanation

The Users table stores information about each user in the application. The Posts table stores posts created by users and uses UserID to connect each post to its creator. The Likes table records which users liked which posts using UserID and PostID. Therefore, Likes helps represent the many-to-many relationship between Users and Posts. The Follow table stores relationships between users using FollowerUserID and FollowedUserID. A user can follow many users, while a user can also have many followers. Together, these tables provide a structured way to store users, posts, likes, and follows.
